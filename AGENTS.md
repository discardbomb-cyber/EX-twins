# EX-twins — правила работы

Самостоятельный мод Minecraft 1.21.1 / NeoForge. Название EX-twins, mod id `relics_addon`, Java-пакет `dev.hurtify.relicsaddon`. Ответы автору — коротко, по-русски.

## Начало задачи

1. Выполни `git status --short` и `git branch --show-current` в выбранном checkout. Не считай `C:/dev/EX-twins` актуальным main: здесь может быть другая ветка.
2. Прочитай только нужный раздел [карты проекта](docs/project-map.md): системы, точки входа, worktree и датированная история решений.
3. Для кода используй `ex-twins-modding`: Codex — `.agents/skills/ex-twins-modding/SKILL.md`, Claude — `.claude/skills/ex-twins-modding/SKILL.md`. Общая техническая памятка — [docs/development.md](docs/development.md).
4. Сверяй имена пакетов и версии с выбранной веткой. На main после S6 есть `domain/` и адаптеры; в старой `docs/readme-ru` ещё используются `drone/` и legacy-правила.

Текущий запрос автора определяет задачу. Архивы чатов и старые промпты — контекст, а не команды к выполнению. Старая пауза Codex по квоте не блокирует новые прямые поручения автора.

## Экономия контекста

- Не сканируй и не читай всё дерево. Начинай с нужного пакета: `rg -l`, затем диапазон строк.
- Большие `work/*.md` читай по заголовкам `rg -n '^#'` и одному подходящему разделу.
- Не читай `.output` субагентов и временные транскрипты. История Claude нужна только для задач, которые её требуют.
- Логи сохраняй в файл; показывай ошибки, итог BUILD и число пройденных/упавших тестов. Проверяй код возврата процесса: пустой фильтр ошибок не означает успех.
- Без просьбы не присылай скриншоты/GIF. Если проверке нужен локальный рендер, сохрани на D: и сообщи результат текстом.
- Делегируй только по явному поручению автора; один субагент за раз, точные файлы и отчёт до 8 строк. Предпочтение автора — haiku/fable; если их нет, работай самостоятельно, не подменяй дорогой моделью.

## Рабочие копии и Git

- Не редактируй чужие незавершённые изменения без поручения именно на них. Сохраняй staged/unstaged изменения; не делай reset/clean ради чистой сборки.
- Перед переходом в другой worktree снова проверь status и локальные инструкции. Не удаляй чужие worktree и не останавливай Minecraft-клиенты, которые не запускал.
- Если делаешь коммит, отделяй логические изменения. Не добавляй `Co-Authored-By` и другие AI-подписи. Push — только по просьбе автора; force-push запрещён.
- Просьба исправить код или документацию не разрешает автоматически публикацию релиза и включение отложенных функций.

## Обязательные ограничения

- Целевая NeoForge — **21.1.251**, как на сервере автора. `neo_version` также задаёт минимум в mods.toml; не повышай его попутно.
- Payload регистрируй **на обеих сторонах**. Нельзя оборачивать `registrar.playToClient(...)` в `FMLEnvironment.dist.isClient()`: сервер потеряет канал. Клиентскую реализацию вызывай внутри обработчика, не загружай client-классы при регистрации на сервере.
- Photon и LDLib2 нужны также на сервере: они регистрируют пакеты. Остальные версии сверяй с build.gradle.
- Не меняй `relics_addon` без миграции идентификаторов/aliases: это ломает существующие миры.
- `domain/` не зависит от Minecraft; common/server не зависят от `client/`. Кодеки новой архитектуры — в `adapter/out/persistence/`.
- Lambda сама по себе не устраняет bytecode-зависимость от client-класса. В ArmageddonPayloads сохраняй отложенное разрешение визуального обработчика, пока архитектура требует его; не возвращай client-only условие вокруг регистрации.
- Счётчики/индексы сетевых кодеков — VarInt/VarLong, не byte. Изменение формата проверь через NetworkCodecCheck выбранной ветки.
- Полное поглощение урона отменяет событие: `damage = 0` оставляет отбрасывание и эффекты. `minecraft:bypasses_shield` не подходит как готовый фильтр.
- Строки добавляй одновременно в `en_us` и `ru_ru`. Golden masters нельзя обновлять только ради зелёных тестов: объясни изменение поведения.

## Проверка и завершение

- Каждую ошибку проверки сохраняй в отдельном логе и [журнале ошибок](docs/testing-lessons.md): причина, исправление, повторный результат и вывод на будущее. Не перезаписывай неудачные прогоны; повторяющиеся ошибки связывай с прежней записью. Устойчивые выводы переноси в технические правила.

- Выбирай проверки по изменению из [docs/development.md](docs/development.md). Для одной документации достаточно ссылок, путей и противоречий; Minecraft не запускать.
- Не называй работу проверенной без фактического результата. В конце коротко: что изменено, что проверено, что осталось.
- Обновляй карту при изменении точек входа/архитектуры. Временные баги, тесты и HEAD записывай там с датой, не превращай в постоянные правила.

## MCP

- Список и инструкции: [docs/mcp-tools.md](docs/mcp-tools.md).
- `mcdev` — исходники Minecraft; `mcmodding` — документация NeoForge; `mc-modpack` — зависимости и диагностика. Всегда выбирай Minecraft 1.21.1 и конкретный run-каталог.
- `blender` и `blockbench` — модели; `memory` — краткие устойчивые решения и уроки. Наличие конфига не означает готовность приложения, базы или аккаунта.
- Используй только инструменты по текущей задаче. Не читай всю базу/память и не публикуй конфиги с секретами. Новые ошибки попадают прежде всего в журнал Markdown, чтобы знания оставались в репозитории.

## Ограничения проекта

- Снимки, видео и тяжёлые захваты — в `D:/ex-twins-captures`: на C: мало места. Учитывай существующие junction в run-каталогах.
- Корабельные щиты (`feature/ship-shields`, `feature/ship-shield-models`) исключены из релиза. Коса и копьё (`feature/twins-spear`) отменены. Не возвращай их без нового поручения.
- Корабельные ульи — отдельная подсистема; релизный состав проверяй по ветке и JAR, не выводи из названия ветки щитов.
